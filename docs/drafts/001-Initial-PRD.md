## 1. 一句话总结 — 在进入细节前的真实判断

你描述的工具确实有用，而且你拥有单人开发者能拥有的最好的护城河：**你自己就是用户**（创始人—市场契合）。但若把需求逐字照搬，就是个陷阱。真实版本如下：

1. **它其实是四个产品。**（a）自带内容的音频*播放器／管理器*；（b）*录音工具*；（c）*文章→音频（TTS）*引擎；（d）*会议→文字→AI*工具。每个产品面对不同用户、不同竞品、不同成本结构。**同时做四个，是单人项目最常见的死法。**

2. **你应当依赖的"独特优势"不是某个功能，而是*成本结构与姿态*。** 因为内容存放在*用户自己的*设备/Google Drive，播放在*设备本地*完成，你免费产品的边际成本约等于 0。这正是抵御你最担心的噩梦（"基础设施成本拖垮项目"）的根本。多数拿了融资的竞品*无法*复制这一点——因为它们的商业模式必须占有你的数据和存储。你的优势＝**私密、无锁定、文件与密钥都归你**——面向高级用户的"反 Spotify、反 Otter"姿态。

3. **唯一具有可怕单位经济模型的，是付费 AI（TTS＋STT＋LLM）。** 千万别按"无限量＋固定月费"来卖。对高级用户用 **BYOK（自带 API 密钥）**，对其他人用**带毛利的预付额度（credits）**。这就是把金融科技的纪律用上：不要去卖一个你无法控制其边际成本的产品。

4. **你的两个用户画像其实是两条不同的市场路线。** "录会议并总结"（Otter/Plaud/Granola 地盘——拥挤、偏企业、靠销售）vs. "把我读的东西变成私人播客"（Speechify/ElevenLabs Reader 地盘——面向个人、自助）。**选一个作切入点。** 以你的背景，我建议主打**"听你想读的东西"**，把会议录音放到第 4 阶段及以后，而非第 1 阶段。

5. **从第一天起就必须绕开两颗法律地雷：**（a）**加州是录音"双方同意"州**——没有同意 UX 的"会议录音器"是负债而非功能；（b）**Google 的 `drive`（完全访问）权限是*受限* scope**，需要每年做一次要花真金白银和时间的 CASA 安全评估。围绕较轻的 `drive.file` 权限来设计，会改变"管理你的 Drive"能做到什么。详见 §6.1、§10。

只记一句话的话：**先做"私密、离线、自带内容的播放器＋局域网管理＋念给我听"，AI 用额度／BYOK 变现，在第一个东西有用户之前，忍住别做会议工具。**

## 2. 问题与愿景

### 2.1 问题
知识工作者（包括你）消费大量*长文输入*——文章、文档、PDF、小说，又产生大量*口头语境*——会议、通话、语音备忘。如今这些散落在 Spotify（音乐、被锁定）、Pocket/Speechify（念给你听、围墙花园）、Otter/Plaud（会议、纯云端、吞数据）和文件系统（你自己的音频、无人管理）之间。没有一个能让你*保留自己的文件、自己的密钥、自己的隐私*，同时还获得出色的移动收听体验。

### 2.2 愿景（一句话）
**一个私密、离线优先的音频伴侣，面向那些想*收听自己东西*的人——他们拥有的文件、转换的文章、录下的对话——无需把数据或存储账单交给平台。**

### 2.3 为何是现在
- 端上音频＋后台／锁屏控制在 Expo/React Native 已是成熟能力。
- TTS、STT 的质量越过了"能连续听一小时"的及格线。
- BYOK 越来越常态化；用户对订阅捆绑和数据收割越来越警惕。
- AI 让单人开发者能做出过去需要一个团队才能做的东西。

## 3. 策略：切入点、用户、定位、"独特优势"

### 3.1 切入点（从这里开始，别全面铺开）
**滩头阵地："听你想读的东西"，面向输入密集的知识工作者**——开发者、研究者、学生、产品经理、金融/法律阅读者，以及重度阅读者（含电子书/同人/长文读者）。核心闭环：

> 看到一篇长文／PDF／章节 → 一键转成音频 → 落入个人"队列"播放列表 → 散步或通勤时离线 1.75× 收听。

这正是你描述的第二个画像（"把文章逐字转成播客"），而且它是更好的切入点，因为它**自助、面向个人、高频，且不被企业销售门槛卡住**。

🔴 **产品经理意见（不要主打会议）：** 会议录音市场（Otter、Fireflies、Granola、Fathom、Plaud、Zoom AI Companion）拥挤，且越来越被会议工具本身打包内置，靠集成＋企业信任＋销售取胜——这是单人开发者*最差*的战场。此外（见 §10）iOS 上你一般**无法录制其他 App 的音频（如 Zoom 通话流）**，只能用麦克风录*房间*的声音。所以你做的其实是*线下面对面*录音器（讲座、1:1、访谈、线下站会），这是个正当但*不同且更小*的细分。可以保留，只是别用它打头阵。

### 3.2 用户画像（及背后的待办任务 JTBD）

| 画像 | 待办任务（JTBD） | 现在用什么 | 为何会换到你这里 |
|---|---|---|---|
| **输入最大化者**（你的第二个画像） | "把我*该*读的东西变成能在走路/开车时听完的音频。" | Speechify、ElevenLabs Reader、Pocket、复制粘贴到 TTS 网站 | 私密、离线、自带语音/密钥、文件归己、无需 $11–30/月 的捆绑 |
| **自托管者／重度收听者** | "用一个出色的移动播放器（带变速、锁屏）播放*我自己的*音频库（讲座、布道、语言包、DJ set、我拥有的有声书）。" | VLC、Plex/Jellyfin、老旧音乐播放器 | 一个干净现代的离线播放器，把*他们自己的*设备/Drive 当后端 |
| **会议记录者**（你的第一个画像——*第 4 阶段及以后*） | "采集线下会议/讲座，得到可搜索的转录＋答案。" | Otter、Plaud、语音备忘＋手记 | 无需会议机器人即可*线下*录音、AI 问答、数据归己的隐私叙事 |

> 注意这三个画像都是不同时刻的*你*。这是真实的创始人—市场契合，但也正因如此范围才会膨胀。强制排序：**输入最大化者 > 重度收听者 > 会议记录者。**

### 3.3 定位陈述
*对于想把自己的阅读和录音变成私密音频的知识工作者，**【App】** 是一个私人的、离线优先的音频伴侣，把你自己的文件和文章变成出色的移动收听体验——与 Spotify 或 Otter 不同，它从不占有你的内容、你的存储或你的数据。*

### 3.4 诚实的"独特优势"
你要"独特优势"。我严谨地说：单人开发者**没有数据网络效应、没有资本、没有分发渠道。**所以"独特优势"这个词已经很慷慨了。你*真正*拥有的是**可防御的定位＋有资金的竞品不会复制的成本结构：**

1. **创始人—市场契合／自用（dogfooding）**——你做你每天真正在用的东西。这被低估，但很真实。
2. **近乎零边际成本的免费层**（自带存储＋端上播放），拿了融资的对手在结构上*无法*匹配，因为占有你的数据就是它们的商业模式。这是你最强、最持久的优势，也正是"基础设施成本拖垮项目"的解药。
3. **以隐私／无锁定／BYOK 作为品牌。** 不信任订阅捆绑与数据收割的人群（开发者、隐私爱好者、量化自我者）虽小但忠诚、LTV 高。
4. **细分社区的喜爱**——选定一个社区（如语言学习者、技术阅读者、同人收听者、讲座复听者），成为他们的*那个*工具。

🔴 **产品经理意见（"独特优势"这个框架本身）：** 别给自己讲一个"某个功能就是护城河"的故事。这些功能单看都不难抄。你的护城河是这套*组合*＋*姿态*＋*你比任何拿钱的对手都更便宜地运营*这个事实。守住这个姿态，别为了追企业收入而漂移成一个云端锁定、数据收割的产品。

## 4. 目标与非目标

### 4.1 目标
- G1. 面向自带内容的、令人愉悦的**离线优先移动播放器**（变速、±5 秒、循环、后台、锁屏）。
- G2. **本机局域网管理**：在同一 WiFi 下用电脑浏览器上传/删除/整理曲库（D8）。
- G3. **一键 文章/PDF/文本 → 音频**，并落入收听队列。
- G4. **可自我维持的经济模型**：免费层边际成本≈0；付费 AI *按次*毛利为正。
- G5. 把**隐私与无锁定**作为品牌承诺（本地优先、用户的 Drive、可选 BYOK）。

### 4.2 非目标（明确不做——你的约束＋我的补充）
- N1. **不是音乐流媒体。** 无曲库、无版权、不买音乐专利。（你的约束——同意，且这也是你的法律护盾。）
- N2. **不做 App 内音频编辑。**（你的约束——同意；编辑是另一个很深的独立产品。）
- N3. **不做文件格式工程**（交给 `expo-audio`）。（你的约束——同意。注意：标签*读取*是另一回事，见 §6.1b。）
- N4.（我补充）**不采集 VoIP／电话通话／其他 App 的音频。** 仅麦克风＋线下房间声。避免平台拒审与通话录音法律。
- N5.（我补充）**不做社交网络。** 分享是一个*文本清单/功能*，不是信息流、关注、私信。忍住这个范围。
- N6.（我补充）**永远不提供"无限 AI"套餐。**

## 5. 竞争格局（让你清楚你*不*在和谁打）

| 领域 | 谁 | 你的差异 |
|---|---|---|
| 音乐流媒体 | Spotify、Apple Music | 不竞争——无曲库。你服务他们*已有/自造*的内容。 |

## 6. 功能需求

按**免费核心**（≈0 边际成本）与**付费 AI**（真实 COGS）组织。每项含需求＋我的注解。

### 6.1 免费核心 — 库与内容管理

**FR-1. 来源：本地设备、Google Drive（可选）、端上局域网 HTTP server。**
- 从以下来源添加曲目：设备文件；用户自己的 Google Drive（可选，`drive.file` App 文件夹）；**通过 App 自己的局域网 HTTP server 推入的上传**（FR-1c——主要管理路径）。
- 上传/删除曲目；创建/重命名/删除播放列表；在列表内拖拽重排；在列表间移动曲目。这些操作在 App 内和通过局域网服务器的 Web UI 都能完成。

⚠️ **风险（Google Drive 权限范围）：** 读取/管理用户*整个* Drive 需要 Google 的**受限 `drive` scope**，会触发 OAuth 审核**＋每年一次的 CASA 二级安全评估**（真金白银且要数周流程）。按 D2，我们用较轻的 **`drive.file` scope**（仅 App 自有文件夹＋用户选中的文件），接受"看不到 Drive 里已有音频"这一限制。引导页须明示此点。

**FR-2. "队列"／智能播放列表。**
- 一个默认自动播放列表，转换好的文章和新录音都落入此处，让核心闭环（"转换→稍后听"）零摩擦。

### 6.1c 免费核心 — 端上局域网 HTTP server *（第一优先级功能 — D8）*

> **对 v0.1 的纠正：** 早期草稿把 "HTTP server" 理解成"App 去抓取某个远程服务器上的音频"并降了优先级。那是误读。真正的功能是**手机自己跑一个 HTTP 服务器**，让用户在**同一 WiFi 下用电脑浏览器管理曲库**——用真键盘和文件选择器来上传、整理，比在手机上舒服太多。这是创始人的第一优先级功能。

**FR-1c. App 在设备上运行 HTTP 服务器。** 在同一 WiFi 下，用户在电脑浏览器打开 `http://<手机IP>:<端口>`，得到一个管理界面来**上传、删除、排序**曲目与播放列表。所有改动都写入同一个库模型（§6.1b）。
- **PIN：** 可选，**默认关闭**（D8）。开启后，浏览器在任何操作前都必须先输 PIN。
- **默认临时运行：** 服务器**只在 App 内管理界面打开时运行**，离开即停——即使不开 PIN，也把暴露窗口压到最小。
- **范围：** 仅局域网；绑定本地接口；绝不暴露到局域网之外。

**服务器包对比（你让我比一比；我无法联网，当前状态请你自行核实）：**

| | `@dr.pogodin/react-native-static-server` | `react-native-nitro-http-server` |
|---|---|---|
| 底层 | 原生 **Lighttpd**；定位是**托管/发送一个静态目录** | 基于 **Nitro Modules**（JSI、高性能、较新） |
| 接收上传/自定义逻辑 | **别扭。** 静态发送（GET）是它的正路；接收 `POST`/上传要靠 Lighttpd 模块（如 WebDAV），且 RN 封装是否暴露这些配置不确定。"只发不收"。 | **合适。** *可编程*服务器——你在 JS 里定义路由/处理函数，`POST` 上传 ＋ `DELETE` ＋ 你的自定义逻辑都是一等公民。 |
| 成熟度 | 更成熟 | 较新；生态/示例更少 |
| 适合 | 发送一个打包好的 Web UI ＋ 音频文件 | **可编程的管理 API**（你需要的） |

**建议：** 你明确要**上传**，那就倾向 **`nitro-http-server`**（可编程、能收请求）。一个可编程服务器可以同时干两件事：`GET` 发送内嵌的管理 Web UI，`POST`/`DELETE` 处理上传/编辑。静态服务器"只发不收"，撑不起管理诉求。

⚠️ **选型前必须核实**（我无法联网查）：（a）**multipart / 流式上传**支持——音频文件可达数百 MB，服务器必须把请求体流式写盘，而非全部读进内存；（b）维护活跃度/最近发布；（c）**Expo ＋ New Architecture 兼容性**——两者都是原生模块，都需要 `expo prebuild` / dev client，**都不能在 Expo Go 里跑**（Nitro 还额外要求 New Architecture）；（d）iOS ＋ Android 双端。

🔴 **产品经理意见（安全——另见 §10 / R-LAN）：** "同一 WiFi" ≠ "可信"。在咖啡店/公司 WiFi 上，同网段任何人都能访问 `手机IP:端口`。PIN 默认关闭意味着只要界面开着，就有一个开放的上传/删除端点。"临时运行"默认设置限制了这一点；局域网明文 HTTP（PIN 与上传可被同网嗅探）是目前接受的权衡。在用于家庭以外环境前，请重新考虑默认开启 PIN。

### 6.1b 库 Manifest 与文件身份 *（基础设施 — D9、D10）*

局域网管理 UI（6.1c）和 Drive 同步（D3）都操作**同一个**模型：一个带版本号的**库 manifest**。音频文件是内容寻址的 blob；manifest 是它们之上的索引——刻意做成类 Git 的结构。

**心智模型（Git 类比）：**
- **音频文件＝blob**，以 `contentId` 内容寻址 → 同内容自动是一个实体（结构性去重）。
- **`library.json`＝索引**，把 `contentId` 映射到 元数据＋播放列表归属＋同步状态。
- **播放列表＝一组有序的 `contentId` 引用。**

**文件身份 — `contentId`（D9）。** `contentId = hash( 精确文件大小 ‖ 时长ms ‖ 采样窗口 )`，其中 `采样窗口` 是在**音频负载区内、跳过 ID3/标签帧**的几段固定窗口（如 3×64 KB，在确定性偏移处）。
- 快（只读几十 KB，而非几百 MB——对 1 小时文件和批量上传很重要）。
- **结构性去重：** 同一段录音传两次 → 同一 `contentId` → 一条 track。（这正是我们选内容指纹而非 UUID 的*原因*。）
- **改标签不变身份**（常见编辑），因为标签区被排除在外。
- **接受的权衡：** 重新编码一个文件 → 新 `contentId` → 当作新 track（罕见）；采样放弃了绝对唯一性*保证*——但把**精确文件大小**作为组成项，意味着大小不同的文件永不撞 ID，无关内容被误合并的概率近乎为零。*实现提醒：* 跳过标签区需要那个本来就要用的元数据解析库；更粗的退化方案是对原始文件头/中/尾取窗口，但那样文件头部的标签一改、身份就变。
- **远期：** 声学指纹（如 Chromaprint/AcoustID），用于在不同编码间识别同一录音。推迟。

**Manifest schema（可扩展——从第一天起带 `schemaVersion`；容忍未知字段）：**

```jsonc
{
  "schemaVersion": 1,
  "tracks": {
    "<contentId>": {
      "contentId": "sha256:...",
      "displayName": "用户编写的名称（覆盖内嵌 title）",
      "description": "",
      "tags": ["focus"],
      "rating": 4,
      "embeddedMetadata": { "title": "...", "artist": "...", "album": "..." },
      "fingerprint": { "size": 57480192, "durationMs": 3600000, "sampleSpec": "v1" },
      "storageRefs": { "local": "file:///.../x.mp3", "drive": "drive:1AbC..." },
      "createdAt": "2026-06-19T10:00:00Z",
      "updatedAt": "2026-06-19T10:00:00Z"
    }
  },
  "playlists": [
    {
      "id": "pl_001",
      "name": "深度工作专注",
      "description": "", "url": "", "tags": [], "author": "Chang", "thumbnail": "",
      "trackRefs": ["<contentId-1>", "<contentId-2>"],   // 顺序＝播放列表顺序
      "createdAt": "...", "updatedAt": "..."
    }
  ]
}
```

- `updatedAt`（每条 track、每个播放列表各一个）就是用于**冲突解决**（D3）的字段：同步冲突时，把本地与 Drive 两个 `updatedAt` 都显示给用户，逐项让其选择谁胜。
- **分享清单**（§6.1a）是一个*投影*：把一个播放列表＋它引用的曲目的显示元数据（及可选 `source`）导出为一份独立 JSON。
- *实务提醒：* 落盘文件名用 **ASCII**（`library.json`），不要用 `摘要.json` 这类非 ASCII 名，以免 URL 编码/跨平台/Drive 出问题；人类可读标签另存为字段。

### 6.1a 播放列表与曲目数据模型（分享投影）

这是**分享导出的形态**——是库 manifest（§6.1b）针对单个播放列表的一个*投影*。库 manifest 是真相之源、以 `contentId` 为键；下面的分享导出是给别人发送用的、扁平化的人类可读子集（D4）。每条被分享的曲目带上它的显示字段；`source` 可选（见下）。

**播放列表对象（Playlist）**

| 字段 | 是否必填 | 类型 | 说明 |
|---|---|---|---|
| `name` | **必填** | string | 唯一必填字段。 |
| `description` | 可选 | string | 自由文本。 |
| `url` | 可选 | string（URL） | 播放列表的规范/来源链接（如可重新拉取处或其"主页"）。 |
| `tags` | 可选 | string[] | 用于筛选/搜索。 |
| `author` | 可选 | string | 创建者/分享者的显示名。 |
| `thumbnail` | 可选 | string（URL/引用） | 封面图。用 URL 或引用，而非内嵌图片字节，让清单保持轻量文本。 |
| `tracks` | （隐含） | Track[] | 有序列表——顺序*即*播放列表顺序。 |

**曲目对象（Track）**

| 字段 | 是否必填 | 类型 | 说明 |
|---|---|---|---|
| `name` | **必填** | string | 唯一必填字段。 |
| `description` | 可选 | string | 自由文本。 |
| `tags` | 可选 | string[] | |
| `embeddedMetadata` | 可选 | object | 音频文件自带的**内嵌标签**——ID3（MP3）、Vorbis comments（FLAC/Ogg）、MP4 atoms（M4A）。常见子字段：`title`、`artist`、`album`、`albumArtist`、`trackNumber`、`year`、`genre`、`artwork`。只读（从文件解析得到），非用户编写。 |
| `source` | **可选**（*已确认*） | string（URL / Drive 文件 ID） | **初期不使用，保留在 schema 中以备将来。** 没有它，分享出的列表是*推荐列表*（接收者看到元数据但无法播放）；有它，同一份清单*可播放*。设为可选，则一种格式两用。 |

✅ **已决定（推荐列表 vs. 可播放）：** `source` 设为**可选**并保留在 schema 中，但**初期不使用**——所以 v1 的分享输出是版权安全的*推荐列表*。该字段予以保留，使将来版本无需改 schema 即可按曲目启用可播放清单。

**格式与设计注解：**
- 用 **JSON** 序列化（可读文本、易分享、易校验）。YAML/TOML 也行；JSON 是稳妥默认。
- 保持**轻量文本**：图片/音频用 URL 或 ID 引用，绝不内嵌字节。这让清单小巧，并保持"不托管音频"姿态。
- `embeddedMetadata` 是从文件*读取*的（需要标签解析库——见 §6.1b）；`name`/`description`/`tags` 是*用户编写*的。两者都存在时（如文件 ID3 的 title vs. 用户的 `name`），需定显示优先级——建议：用户编写的 `name` 优先，回退到内嵌 `title`。
- 从第一天起给清单加版本号（`schemaVersion`），让未来字段不破坏旧导入。

分享导出示例（示意）：

```json
{
  "schemaVersion": 1,
  "name": "深度工作专注",
  "description": "本周我转换的长文",
  "author": "Chang",
  "tags": ["focus", "tech"],
  "thumbnail": "https://example.com/cover.jpg",
  "url": "https://example.com/playlists/deep-work",
  "tracks": [
    {
      "name": "为什么要用无聊的基础设施",
      "description": "由博客文章转换",
      "tags": ["devops"],
      "embeddedMetadata": { "artist": "TTS: voice-A", "album": "阅读队列" },
      "source": "drive:1AbC...xyz"
    },
    {
      "name": "第三章 —（公有领域小说）",
      "embeddedMetadata": { "title": "第三章" }
    }
  ]
}
```
*（第二条曲目无 `source` → 它是推荐条目，不可播放。）*

### 6.2 免费核心 — 播放器

**FR-3. 播放控制。** 播放/暂停、上一首/下一首、**±5 秒定位**、进度条。
**FR-4. 循环模式。** 关闭／单曲循环／全部循环。
**FR-5. 变速。** 1.0／1.25／1.5／1.75／2.0×（为语言学习者考虑 0.75×；后续可加任意滑杆）。
**FR-6. 后台播放。** App 退到后台/熄屏时继续播放。
**FR-7. 锁屏与通知栏控制＋远程指令中心**（播放/暂停/定位/切歌、封面、标题）。

⚠️ **风险（平台繁琐）：** 后台音频、锁屏 `MPNowPlayingInfoCenter`/Android `MediaSession`、音频焦点处理是这次开发*最折磨*的部分——来电中断、蓝牙/耳机按键、压低音量（ducking）。这里要留足时间；"像原生 vs. 像卡顿"就在这里分胜负。（CarPlay/Android Auto 已按 D5 排除在范围外；蓝牙播放与锁屏控制开箱即用，足够"开车时用蓝牙听"。）

### 6.3 免费核心 — 录音

**FR-8. App 内录音 → 可配置的默认文件夹。**
- 录制麦克风音频；保存到用户可配置的默认文件夹（建议默认本地；可选 App 的 Drive 文件夹）。
- 录音出现在库中，可播放、可入队、（第 4 阶段及以后）可转录。

⚠️ **风险（同意＋平台）：** 见 §10。即便是*个人*录音器，一旦你拿它来宣传会议场景，就需要同意姿态。录音保持**仅麦克风/线下房间声**；不要尝试系统/其他 App/通话音频。

### 6.4 免费核心 — 离线优先与免登录

**FR-9. 完全离线可用。** 播放已下载/本地曲目、录音、管理本地列表、运行局域网管理服务器——**无需网络、无需登录。**
**FR-10. 登录可选，仅门控云/AI。** 仅以下功能需要身份：Drive 同步、（未来的）播放列表分享、托管（非 BYOK）AI。

**FR-10b. Drive 同步（可选、手动优先 — D3）。** 用户选择开启后，库 manifest（§6.1b）＋音频 blob 同步到他们自己的 Drive App 文件夹，用于**备份＋跨设备**。
- **默认手动同步**；自动同步以后作为可选项。
- **不阻塞：** 同步在后台进行，绝不阻塞播放、录音或管理。
- **冲突解决：** 逐项把**本地**与 **Drive** 的 `updatedAt` 都显示给用户，让其选择谁胜。无静默自动合并；高级合并推迟。

🔴 **产品经理意见（架构）：** 本地存储仍是真相之源；Drive 是可选的备份/同步目标。因为身份是内容指纹（§6.1b），跨设备匹配基本免费——同一文件在两台设备上解析为同一 `contentId`。剩下的工作是 manifest 协调（由 `updatedAt` 驱动的冲突 UI），它有界，对"可选、手动优先"的同步而言是恰到好处的复杂度。

### 6.5 免费核心 — 播放列表分享 *（推迟——不在 v1；D4）*

**FR-11. 把播放列表作为文本清单分享**（即 §6.1a 的投影）给已注册/已登录用户。**永不传输任何音频文件**——只传元数据结构。

D4＋§6.1a 已把它界定清楚，旧的争论基本尘埃落定。剩下的：
- **推荐列表 vs. 可播放清单**由每条曲目的可选 `source` 字段决定（§6.1a）。无 source 的清单是版权安全的参考列表；带 source 的可播放——*前提是*接收者能访问这些来源。
- **传输方式：** 虽然定了"账号"，但要注意清单只是文本——它也可以作为文件/二维码/剪贴板传递。把账号用在*目录/权限*层（当你想要私密、可撤销分享时）；别让"账号"暗示你必须托管任何东西。

⚠️ **风险（版权/DMCA）：** 分享会把"个人使用"变成"传播"。纯文本、不托管音频的模型是最强护盾：你传的是*关于*音频的元数据，而非音频本身。加入 `source` URL/ID 会重新引入一些风险（你现在指向了内容）——在上线前，ToS 须明示用户只能分享自己有权分享的内容，并提供下架通道。

### 6.6 付费 AI — 文本 → 音频（TTS）— *切入点的兑现*

**FR-12. 把 文章/PDF/粘贴文本/电子书章节 → 音频曲目。**
- 输入：粘贴文本、URL（抓取＋正文提取）、上传的 PDF/EPUB、从其他 App 的分享菜单（"分享到【App】"）。
- 输出：保存到用户库/Drive 的音频文件，自动加入队列。
- 多语音选择；长内容分块；可断点续传。

⚠️ **风险／COGS：** TTS 是**按量计费**（按字符/秒）。这是会拖垮固定费率套餐的成本项。模型见 §9。**缓解：**预付额度、硬性上限、**去重/缓存**（同样文本→复用音频）、对高级用户用 **BYOK**。

🔴 **产品经理意见（小说 TTS 的版权）：** 把*受版权保护*的小说转成音频供*个人*使用属于灰色地带；*传播*它（通过分享）则构成侵权。让 TTS 输出**默认私密**，别让分享功能变成有声书盗版管道。围绕*文章、文档、你自己的写作、公有领域与你拥有的电子书*来营销——而不是"把任何畅销书变成有声书"。

### 6.7 付费 AI — 音频 → 文本＋问 AI — *第 4 阶段及以后*

**FR-13. 把录音/曲目转录为文本。**
**FR-14. 基于该转录向 AI 提问**（总结、行动项、"我们关于 X 决定了什么"）。

⚠️ **风险／COGS：** STT（按音频分钟）＋ LLM（按 token）*都*按量计费。同一原则：额度＋上限＋BYOK。长会议＋话痨式问答正是账单飙升之处。

⚠️ **风险（隐私与数据处理）：** 会议转录含机密信息/个人信息。如果你把音频路由经第三方 AI API，你就继承了数据处理的期望（任何企业用户都会问"我的音频去了哪"）。你的隐私姿态是*资产*——把它写清楚：尽量端上处理、不拿用户数据训练、提供删除控制、用 BYOK 让数据进*他们自己*的服务商账户。

## 7. 横切需求

- **隐私：** 本地优先；用大白话明示数据流向；不出售/不挖掘数据；删除即真删除。
- **无障碍：** 变速/大字号/语音控制对此人群很重要（也利于 App Store 好感）。
- **性能：** 本地文件即时起播；TTS/STT 任务可续传；离线优雅降级；大文件指纹/上传走流式。
- **可观测（成本！）：** 你*必须*从第一天起追踪每用户 AI 用量与每次操作 COGS，否则无法安全定价。这就是金融科技直觉——把钱仪表化。

```
└──────────────┘      └──────────────────┘      └────────┬──────────────┘
                                                          │（按量 或 用户密钥）
                                                 ┌────────▼──────────────┐
                                                 │ AI 服务商（TTS/STT/LLM）│
                                                 └────────────────────────┘
```

**成本后果（最关键的部分）：**
- **边际成本≈0。** 文件＝用户设备＋用户自己的 Drive。播放＝设备。管理＝局域网（无云）。同步＝用户的 Drive。离线优先＝无服务器往返。
- **有牵引力之前固定成本≈0。** v1 完全无后端；唯一可选的服务器（AI 代理）是无服务器、跑免费额度，且只有在你提供非 BYOK AI 时才出现。
- **唯一的变动成本是 AI**，用 BYOK/额度封顶（§9）。失控的基础设施成本噩梦在结构上被限定住了。

**关键架构决策（已锁定）：**
1. **Google 权限：** `drive.file`＋App 文件夹（避开 CASA）。（§6.1 / D2）
2. **身份：** 内容指纹 `contentId`，结构性去重，不用 UUID。（§6.1b / D9）
3. **单一模型：** `library.json` manifest 同时驱动局域网管理与 Drive 同步。（§6.1b / D10）
4. **同步：** 可选、手动优先、基于 `updatedAt` 的冲突解决。（§6.4 / D3）
5. **管理：** 端上局域网 HTTP server 是第一优先级功能。（§6.1c / D8）
6. **分享不托管音频**（仅文本清单）。（§6.5 / D4）

🔴 **产品经理意见（IAP 这头大象）：** 苹果/谷歌抽取应用内订阅的 **15–30%**。这笔税在 COGS *之前*就吃掉你的 AI 毛利。要把它建模进去。（近期美国关于外部支付链接的判决存在，规则在变化——**在你设计计费前，先核实当前 App Store/Play 规则**，因为它们会变，我无法假定今天的状态。）BYOK 能绕开*你的* COGS，但你仍想要付费层；定价时把平台抽成算进去。

## 9. 变现与单位经济模型（金融科技视角）

### 9.1 模型
- **免费：** 整个核心播放器＋管理器＋局域网管理＋录音＋离线＋（可选）基础分享。边际成本≈0，因此慷慨的免费层*没问题*，且是你的获客引擎。
- **付费——两条腿：**
  - **BYOK（"Pro／自带密钥"）**——低固定月费，解锁 AI 功能，*但用户付自己服务商的钱*。你的 COGS≈0。高毛利，吸引隐私/高级人群，给你的风险封顶。
  - **托管额度（"Plus"）**——为 TTS 分钟/STT 分钟/AI 问题预付额度，按**高于 COGS 的加价**定价。为非技术用户提供便利。硬性上限防止账单失控。

🔴 **产品经理意见（绝对别这么做）：** **不要**按固定月费提供"无限 TTS/转录"。一个把 50 本小说转音频或转录 100 小时的重度用户，能抹掉许多用户一个月的收入。这就是"对按量 COGS 收固定费"的经典死亡陷阱。

### 9.2 示意性 COGS 模型 — *请自行核实当前价格*
> 我这里无法联网查实时价格，且价格每月都在变，所以把数字当作**待你填入的占位符**，不是事实。重点是这个*框架*。

| 操作 | 成本驱动因素 | 大致数量级* | 你如何收费 |
|---|---|---|---|
| TTS | 每约 1k 字符 / 每分钟音频 | "每篇文章几美分"区间 | 额度 / BYOK |
| STT（转录） | 每音频分钟 | "不到一美分 → 约 1 美分/分钟"区间 | 额度 / BYOK |
| AI 问答 | 每 token（入＋出） | "不到一美分 → 每问几美分" | 额度 / BYOK |

*\*仅数量级——定价前请**查今天 ElevenLabs/OpenAI/Deepgram/Whisper 等的实时价格并重算**。*

**规则：** 给每个额度定价，使得 **(每额度售价) − (每额度 COGS) − (IAP 抽成) > 0**，且留毛利。追踪每用户实际用量，以便发现少数否则会亏本的"鲸鱼用户"，并对其封顶。

### 9.3 盈亏平衡逻辑（为何能自我维持）
因为固定成本≈0 且免费层边际成本≈0，**盈亏平衡 ≈（少量付费用户）×（毛利）>（你那点无服务器账单＋AI 垫付）**。你不需要规模就能存活——你需要的是*每个付费操作的非负单位经济*和*接近零的固定成本*。对单人项目而言这就是全部，而你的架构已经支持这一点。

## 11. MVP 范围与分阶段路线图（最重要的一节）

*已反映锁定的决策记录：个人必备项（局域网管理＋曲库）打头阵；面向他人的切入点（TTS）随后；Drive 同步再往后。*

**第 0 阶段 — 个人 MVP（自用；为*你自己*而建）：**
- **库基础：** `library.json` manifest ＋ 内容指纹身份（§6.1b）。这是其他一切挂靠其上的脊梁——先做它。

- App 内录音 → 可配置文件夹（个人使用框架）。
- 完全离线、免登录。
*目标：你每天都在用它。**零后端、零账号。***

**第 1 阶段 — 切入点（让它对他人有用）：**
- **TTS：文章/URL/PDF/粘贴 → 音频 → 队列。** 分享菜单"分享到【App】"。
- AI 成本**先用 BYOK 处理**（用户自带密钥 → 你的 COGS≈0）。只有当你提供托管（非 BYOK）路径时，才需要那个薄薄的无服务器 AI 代理，这是*唯一*的服务器组件。
- **变现：TODO——推迟。** 暂不设付费墙。但从第一天起就埋点每用户/每操作的 AI 用量，以便日后无需重构即可定价。
*目标：让"听我想读的东西"的闭环像魔法一样；除你之外也有人在用。*

**第 2 阶段 — Drive 同步＋打磨：**
- **可选 Drive 同步**（D3）：备份＋跨设备，手动优先，`updatedAt` 冲突 UI，不阻塞。
- 更好语音；EPUB；队列/智能列表体验。
- （CarPlay/Android Auto 仍**不在范围内**，D5。）

**第 3 阶段 — 变现（重议 D6）：**

**第 4 阶段及以后 — 会议与分享（推迟的赌注）：**

## 12. 成功指标

- **北极星：** *每周活跃用户的收听分钟数*（证明核心闭环成立）。

-（第 4 阶段及以后）记录者：每用户创建的转录数；每个转录被问的问题数。
